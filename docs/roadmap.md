# softBASIC — Internal Product Roadmap

> Internal document. Not for publication. Last updated: 2026-08-07.

---

## Versioning model

**Trunk-based development.** All work lands on `main`. Patch bumps (`0.x.Y`) are continuous — any fix, doc update, or small feature that ships independently. Minor bumps (`0.X.0`) mark milestone completions, each representing a discrete capability step. Currently at `v0.4.3`, but this understates where things actually are: Milestone 1 shipped as `v0.3.0`, Milestone 2 (professional editor) shipped as `v0.4.0` — but **Milestone 3 (save/load) was never given its own version bump or release-notes entry**, despite closing out a whole milestone (which the versioning model itself says warrants a *minor* bump, not a patch). `v0.4.1`/`v0.4.2` covered unrelated editor bug fixes that happened to land around the same time; `v0.4.3` covers a compiler-limitation fix discovered *while building* Milestone 3 (see "Known deferred issues" #6 below) — but the feature itself was folded into the version-number background noise rather than announced. **This needs a proper `v0.5.0` cut before calling Milestone 3 actually released**, not just implemented.

**Public beta vs. v1.0:** these are two distinct bars, not the same milestone. Public beta (Milestone 3) means someone can design, build, and ship a complete game anonymously — gated on game state save/load, not accounts. (Production error tracking was also on this list until scoping the milestone turned up that it's already shipped — see Milestone 3.) v1.0 (Milestone 6) additionally requires accounts, sharing, the gallery, and the package ecosystem (Milestones 4–6). Reframed 2026-08-02 after concluding accounts weren't actually the missing link for "can someone build a full game" — persistent state was.

Milestones 1–6 are fully defined. Milestones 7–14 are intentionally loose — trajectory markers only. Each will be fully scoped and planned before implementation begins, so detail accumulates just-in-time rather than speculating years ahead.

## Current state (v0.4.3)

Shipped and working:
- Full softBASIC compiler (lexer → parser → transpiler → PIXI.js runtime)
- Sprite, animatedsprite, tilemap, text, drawing, audio, collision, input modules
- Scene management (`Scene` base class + `SceneManager`), camera (`camera` module), and world/HUD layers (`world` + `hud`, replacing the deprecated `stage` module) — closes out Milestone 1
- Professional Monaco-based editor — autocomplete, hover documentation, parameter hints, live error underlining, and dynamic symbol resolution (user-defined functions/classes/variables, not just the built-in library) — closes out Milestone 2, see below
- Typed collections, class inheritance, `new` keyword, dependency-ordered multi-file builds
- Folder system, asset panel, import/export, package registry
- Landing page with live game preview
- Demos page, launched with a Wolfenstein-style raycaster tech demo
- Production error tracking (Sentry) — React app crashes and sandboxed game-iframe runtime errors both captured, the latter with full project source attached for reproduction; shipped 2026-06-17, DSN confirmed live in the production deployment
- `oninit` lifecycle hook — the only hook that runs *before* asset preloading, so a project can configure the runtime while there are still no textures (shipped 2026-08-04, see `docs/language/library-roadmap.md` P11). Closed a genuine language gap: every other hook fired post-preload, so there was no init phase at all. Required two-phase module initialisation in the transpiler — a root's inert declarations are emitted inline while its own top-level statements are deferred to `_sb._deferModuleBody` and replayed after preload — which is what let the transpiled block move ahead of asset loading in `bootstrapper.html`
- `world.setPixelPerfect(v)` and `camera.setZoom(z)`/`camera.zoom()` — crisp pixel-art scaling plus a camera zoom that magnifies the whole world uniformly (tilemap, sprites, everything) without touching any object's own position/collision math (shipped 2026-08-04, see `docs/language/library-roadmap.md` P12). `setPixelPerfect` is the direct payoff of `oninit` existing: called before any texture loads, it needs no retroactive fix-up
- `pathfinding` module — A* over a `TileMapSet`'s named layers, so sprites can navigate around obstacles instead of moving in a straight line. `pathfinding.setup(tileMapSet, blockingLayers)` builds a nav grid once from whichever layers are flagged as solid; `pathfinding.navigateTo(sprite, x, y, speed)` is cheap to call every frame with a live target (a fresh path is only computed when the target moves to a new grid cell and a cooldown has elapsed), `isNavigating(sprite)`/`stopNavigating(sprite)` round out the API. 8-directional movement with corner-cut prevention, snaps to the nearest walkable tile rather than failing on a blocked/off-grid target (shipped 2026-08-07, see `docs/language/library-roadmap.md` P13). Built to unblock the upcoming bullet-hell shooter demo's enemy AI. Design: `docs/superpowers/specs/2026-08-07-pathfinding-design.md`. No shared flow-field optimization for many-agents-to-one-target and no dynamic (sprite-vs-sprite) obstacle avoidance in this iteration — every sprite paths independently against the static tilemap only.
- Tilemap markers — tagged position markers paintable in the Tilemap Editor (a new marker layer kind, alongside ordinary tile layers) and queryable at runtime via `tileMapSet.markersByTag(tag)`. A deliberate, scoped re-opening of the "no tile-property metadata" non-goal recorded when the Tilemap Editor originally shipped (Milestone 12), driven by the upcoming bullet-hell shooter demo's need to place mob-spawn/weapon-pickup points visually rather than hardcoding coordinates (shipped 2026-08-10, see `docs/language/library-roadmap.md` P14). Design: `docs/superpowers/specs/2026-08-10-tilemap-markers-design.md`.

12. ~~Calling a method on a **function-scoped** object local and using its **return value in an expression** emitted a name that is `undefined` at runtime~~ **[RESOLVED, 2026-08-04]** — `dim s as sprite(...)` inside a function compiled correctly for its constructor assignment and for void method calls used as bare statements, but `print string.str(s.width())` emitted `main.onenter.s.width()` instead of `onenter_s.width()`, throwing `Cannot read properties of undefined`. Root cause was **not** `formatSymbol` (where the wrong string merely became visible): two parser rules handle `obj.method(...)` depending on grammatical context, and they derived the call target from different sources of truth. The statement path (`ObjectPropertyRule`) builds it from the *instance* symbol via `formatSymbol(ownerSymbol)`; the expression path (`VariableFactorRule`) computed exactly the same value and then **discarded it**, delegating to `FunctionFactorRule` so that `FunctionTermRule` re-derived the callee from the *method* symbol's `fullScope` — the lexical scope chain recorded by `Symbols.clone()` at declaration time (`main.onenter.s`). That is a declaration path, not a JS access path, and the two only coincide for **module-scoped** instances (`main.s` === `main.s`), which is why nothing caught it: every shipped tutorial reaches instance members through `self.x` (a separate rule) or declares them at module level. Surfaced while building the coins-platformer demo, which needed `dim t as tilemap(...)` in a scene's `onenter()` and then read `t.tileAt(x, y)`. Fixed by threading the already-resolved receiver from the call site into `FunctionTermNode`, so both contexts now resolve it from the instance symbol and cannot disagree — deliberately keeping `FunctionTermNode` (and therefore `BaseParameterValidatorNode` arity/type checking) rather than switching to the unvalidated `PropertyMethodTermNode` that `SelfFactorRule` uses. Investigation also turned up two shapes the original report assumed were safe: **typed function parameters** (`s as sprite`), which `VariableListRule` registers as Object symbols through the same clone path, and **locals inside class methods**. Gated by `tests/lib/Basic4WebGL/unit/transpiler/objectInstanceScoping.test.ts` (18 tests; 9 failed / 9 passed before the fix, splitting exactly along broken vs. already-correct paths) and `cypress/e2e/objectInstanceScoping.cy.ts` (asserts printed *values*, not just absence of `ERR`, so a program that runs but computes the wrong thing still fails — confirmed non-vacuous by reverting the fix and watching all 4 fail). Design: `docs/superpowers/specs/2026-08-04-object-instance-receiver-resolution-design.md`. Not recorded in `docs/language/library-roadmap.md` — that file's "Fixed Bugs" section tracks runtime engine/library defects, and this changes no softBASIC API surface.
13. ~~A class-scope **array field** indexed through `self` and **read in expression position** transpiled to a JavaScript function call instead of an array index~~ **[RESOLVED, 2026-08-04]** — `v = self.coins(i)` emitted `this.coins(readit_i)` rather than `this.coins[readit_i]`, throwing `this.coins is not a function` at runtime with zero compile diagnostics. Root cause: softBASIC spells array indexing and method calls identically (`name(args)`), so `self.member(...)` is genuinely ambiguous and can only be settled by asking the symbol table what kind of member it is. Two rules handle that form depending on grammatical context, and only one could settle it: the **statement** path (`SelfRule`) disambiguates *syntactically* on a trailing `=` — a method call can never sit on the left of an assignment — so indexed **writes** were always correct and `SelfArrayAssignNode`/`SelfArrayAssignRule` already existed to emit them. The **expression** path (`SelfFactorRule`) has no such lookahead token, must consult the symbol table instead, and never did: it unconditionally returned a `PropertyMethodTermNode` for every `self.x(...)`, despite already performing a class-scope symbol lookup a few lines lower to recover the `dataType` of a non-indexed `self.property` read. The information needed was already being fetched by that rule for another purpose; the ambiguous path just never asked. Survived this long because every shipped tutorial touching a class array either passes it whole to an `array.*` function (bare, unambiguous) or writes by index (disambiguated by `=`) — reading one back by index inside a method is what the coins-platformer demo first needed. Fixed by resolving the member's kind against the enclosing class scope (walking the inheritance chain) via a new `resolveSelfMember` helper and emitting a new `SelfArrayLookupNode` — the read-side mirror of the existing write pair — only when the member is provably an `Array`-kind class member and provably **not** a method. **A method of that name always wins**, which is what makes the change provably non-breaking: no `self.x(...)` that compiles today can change meaning. The pre-existing `dataType` walk in the same rule was folded onto the same helper (semantics preserved exactly via an `accept` predicate) so the two class-scope lookups cannot drift apart. Investigation corrected two assumptions in the original report: indexed **writes** were never broken, and class-scope **dictionary** fields are affected but *differently* — a loud compile error rather than a silent miscompile (see #14). Fixed shapes beyond the reported one: reads in arithmetic, comparisons/`if`, `while` conditions, `print` and module-function arguments, `return`, nested as their own index, multi-dimensional fields (`this.grid[1][2]`), reads inside **constructors**, and **inherited** array fields. Gated by `tests/lib/Basic4WebGL/unit/transpiler/selfArrayFieldAccess.test.ts` (29 tests; 16 failed / 13 passed with the fix disabled, splitting exactly along broken vs. already-correct paths) and `cypress/e2e/selfArrayFieldAccess.cy.ts` (3 specs asserting printed *values*, each writing by index and reading back by index so a regression in either direction changes the output — confirmed non-vacuous by disabling the fix and watching all 3 fail). Design: `docs/superpowers/specs/2026-08-04-self-array-field-indexing-design.md`.
14. ~~**Class-scope collection fields are only reachable through `self` for arrays, and only by plain index**~~ **[RESOLVED, 2026-08-05]** — all three shapes shipped: (a) **dictionary fields via `self`** — `self.scores["a"]` read/write now parses via new `OpenBracket` branches in `SelfFactorRule`/`SelfRule`, emitting through two new chain-generic nodes, `SelfDictLookupNode`/`SelfDictAssignNode` (`_sbDictGet(this.scores,"a")` / `this.scores.set("a",v);`), siblings of the existing `SelfArrayLookupNode`/`SelfArrayAssignNode` pair from #13; (b) **array/dict fields accessed from outside the class** (`someInstance.items(0)`, `someInstance.scores["a"]`) — both read and write now resolve via `Symbols.getInScope(member, kind, instanceVarName)`, the same lookup `DimRule`'s `clone()` already sets up for external method calls, and **reuse the exact same nodes as (a)** rather than a parallel `Instance*` pair — `SelfArrayLookupNode`/`SelfDictLookupNode`/etc. take a plain JS receiver-chain string, not a self-specific one, so they were never actually self-exclusive; (c) **member access on an array element via `self`** (`self.bullets(0).getX()`) — `TypedElementAccessNode`/`TypedElementAccessRule` (which already supported this for non-`self` typed arrays) now accept an optional pre-built `chain` string as an alternative to a `collectionSymbol`-derived one, wired into both `SelfFactorRule` (expression) and `SelfRule` (statement, which had **no** array-field awareness at all before this). Every branch preserves #13's "a method always wins" disambiguation rule — resolved via `getInScope`/`resolveSelfMember` against `Function` kind before ever treating a name as a collection field, so no code that compiled before this change can change meaning. Chaining a call onto a typed element read through an **external** instance (`someInstance.bullets(0).getX()`) was explicitly scoped out — not one of the three reported shapes — and is noted as a small follow-on below. **Found and fixed along the way, not part of the original report:** `TypedElementAccessNode`'s chained-method-name resolution (`enemies(0).someMethod()`, `dict["k"].someMethod()`) never lowercased the method name at four pre-existing call sites (two in `VariableFactorRule`, two in `VariableRule`) — but every softBASIC function/method name *is* always lowercased at declaration (`FunctionRule`), so any typed-collection chained call to a method with a capital letter in its name (`.getX()`, `.setPosition()`) would throw `<name> is not a function` at runtime with zero compile diagnostics, silent until executed. Never caught because no existing test both used a mixed-case method name on this path *and* executed the compiled JS rather than string-matching it — confirmed via a real-execution regression test (`tests/scratch/selfCollectionSmoke.test.ts`, kept `.skip`'d as scratch) that would have thrown before the fix. Fixed at the source (lowercase the token once, at all six now-shared call sites) rather than patched per-node. One pre-existing test (`typed-collections.test.ts`'s `players["Alice"].setPosition(...)` case) asserted the old, never-actually-callable mixed-case output and was corrected to the real lowercase form. Design/plan: `docs/superpowers/plans/2026-08-05-self-collection-field-access.md`. Tests: `tests/lib/Basic4WebGL/unit/transpiler/selfDictFieldAccess.test.ts`, `instanceCollectionFieldAccess.test.ts`, `selfTypedElementAccess.test.ts`.
15. ~~**A class can declare an array field and a method with the same name with no diagnostic at either declaration site, and it crashes at runtime**~~ **[RESOLVED, 2026-08-06]** — `Symbols.add()`/`addTyped()`'s duplicate-declaration check was scoped per symbol *kind*, not per name (`dim items(3)` and `function items()` never collided because 'Array' and 'Function' are different kinds), so declaring both coexisted silently and crashed at runtime regardless of which the compiler resolved `self.items(0)` to — the class body's inline method assignment always runs before the field's deferred initializer (`RootRule`'s two-phase init split), so the field's assignment always clobbers the method's prototype slot last, no matter the source order. Fixed with a new, optional, constructor-injected hook on `Symbols` (`findCrossKindCollision`, mirroring how `isMatchingType` is already injected) — kept out of the generic `CompilerLib` layer entirely, since "class inheritance" is a Basic4WebGL concept, not a `Symbols` one. The Basic4WebGL-supplied hook walks from the class currently being declared into, up through `parentClassName` (the same chain `resolveSelfMember` already walks for *lookups*, now applied at *declaration* time), checking each level — starting with the class itself, so same-class collisions are caught too — for an existing symbol of the same name but a *different* kind; a same-kind match (a child class overriding a parent method, or shadowing a parent field) is correctly left alone. Also added a new generic primitive this needed: `Symbols.findAnyInScope(name, scopeName)`, a kind-agnostic name+scope lookup (every existing lookup filters by kind). Verified: same-class collisions in either declaration order, cross-class collisions through inheritance in either direction, a legitimate same-kind override across inheritance still compiles, two unrelated classes each using the same member name don't collide, and ordinary classes with no collision are unaffected. Design/plan discussed inline, not written up separately. Tests: `tests/lib/CompilerLib/unit/symbols/symbolTable.test.ts` (generic hook mechanism), `tests/lib/Basic4WebGL/unit/transpiler/classMemberCollision.test.ts` (real compiler integration). **Deliberately scoped to class members only**, matching how this was reported — module scope (`main.items`) has the textbook-identical deferred-init clobbering bug (a module-level `function items()` + `dim items(3)` would crash the same way), tracked as a new, separate follow-up (#22) below rather than silently fixed or silently left undocumented.
16. ~~**Every object instance's own `onupdate(delta)` silently stopped being dispatched by the frame loop** after the first `world.remove()`/`hud.remove()`/`world.clear()`/`hud.clear()`/scene switch~~ **[RESOLVED, 2026-08-04]** — the first **runtime engine** bug of this session rather than a compiler one. Instances added via `world.add()`/`hud.add()` kept correct `onupdate` methods and ran correctly when invoked directly, but the real `app.ticker` loop never called them again; entirely silent, no error of any kind. The report's second half, found during verification and *not* in the original triage, is the mirror symptom: removed objects never **stopped** updating either — `world.remove(enemy)` detached the display handle so the enemy vanished from screen while its `onupdate` ran forever, an invisible zombie still mutating game state. Root cause: `softBasicEngine.js` builds the global `_sb` by spreading all 14 engine modules once at script-eval time, which copies the *reference* held in `_sbLifecycle._sbInstances` into a **second independent property slot** on `_sb`. Mutating the shared array through either slot is safe; **reassigning** either detaches them. `stage.js` reassigned in five places (four `.filter(...)` calls plus `clear()`'s `= []`), each writing the **module's** slot by hardcoded name — while every reader goes through `_sb`: instance dispatch is `_sbLifecycle._update.call(this)` with `this` bound to `_sb`, and `bootstrapper.html`'s key listeners read `_sb._sbInstances` directly (so instance `onkeydown`/`onkeyup` were broken by the same divergence). After the first mutation, `_sb`'s slot held a permanently orphaned array; later `world.add()` calls pushed onto the new one the loop never read again. Those five lines were the **only** writes to a hardcoded module property anywhere in the engine — every other module (`camera`, `scene`, `input`, and `lifecycle`'s own `_deferredModuleBodies`) reads and writes its state through `this`, which is safe precisely because `this` is always `_sb`; `clear()` already calling `this._cameraReset()` (a `camera.js` method) proved that. 18. ~~**Every softBASIC game ran ~16.67x slower than its own documented contract** — the `delta` handed to every `onupdate(delta)` was PIXI's frame-count-normalised value (~1.0 per frame), not milliseconds~~ **[RESOLVED, 2026-08-04]** — the second **runtime engine** bug of this session, and the most cross-cutting: every moving object in every game, tutorial and demo depended on it. `bootstrapper.html` wired the frame loop as `app.ticker.add((ticker) => _sb._update(ticker.deltaTime))`. PIXI's `Ticker` exposes two different numbers — `deltaTime` is normalised so that 1.0 means "one 60fps frame", while `deltaMS` is the same quantity in milliseconds — and the loop took the wrong one. That value flowed unmodified through `_sb._update(delta)` into every module-level and every instance `onupdate(delta)`. But the contract is milliseconds in three independent places: `src/docs/language-guide/lifecycle.md` ("the elapsed time in milliseconds since the last frame"), `src/docs/api-reference/scene.md` ("Time since last frame in milliseconds"), and every tutorial doing frame-rate-independent movement, which writes `speed * delta / 1000`. So `dt = delta / 1000` computed ~0.001 instead of ~0.01667. Tutorial 7 shows the discrepancy at its most concrete: it accumulates `timer = timer + delta` and tells the reader the score "ticks up by one every second" at `timer >= 1000` — in reality it ticked once every ~16.7 seconds, and inside the e2e suite's own window that branch **never fired at all**. Across every sampled frame `deltaMS / deltaTime` was **exactly** `1000/60` with zero variance — which is what makes `deltaMS` provably the correct replacement rather than merely a closer one: it is `deltaTime` scaled by a constant, carrying the identical `ticker.speed` scaling and `minFPS` clamp, so the swap is a pure unit conversion with no behavioural side effect. Left alone, fixing the units would have made every camera shake finish ~16.67x too early (a 0.5s shake completing in 2 frames), and nothing in the suite covered shake duration, so it would have shipped silently. Two near-misses were checked and are genuinely unaffected: `animatedSprite.js`'s `animationSpeed = def.fps / 60` looks like the same mistake but PIXI's `AnimatedSprite` self-drives from `PIXI.Ticker.shared`, a *different ticker object* from `app.ticker` (verified in-browser that they are not identical), and `camera.follow`'s `speed` is documented as a per-frame lerp factor that never reads `delta`. Non-vacuity: every Cypress spec prints a frame-count checkpoint driven by a counter independent of delta's *value*, so a game that never booted fails there rather than passing silently, and every delta assertion is two-sided so an accidental over-scaling is rejected too — confirmed by reverting the fix and watching all 4 fail with messages naming the real bug while their controls still passed. Survived this long because `tutorials.cy.ts` and `demos.cy.ts` contain exactly one assertion each (`ERR` must not exist) and this bug emits no error, Vitest cannot instantiate a `PIXI.Ticker` so no unit test ever saw a real frame delta, and the symptom is uniquely un-alarming: a sprite that moves slowly looks like a sprite with a low `speed` constant, and an author's natural fix — raise `speed` until it looks right — silently bakes the 16.67x error in and destroys the evidence. Introduced by the fix for "Bug 1 — `onupdate()` never fires" (`docs/language/library-roadmap.md`), which correctly connected `_update` to the ticker and picked the wrong one of its two delta properties; because `onupdate` went from never firing to firing, the change read as an unambiguous success and the units were never questioned. Design: `docs/superpowers/specs/2026-08-04-delta-units-fix-design.md`.

Confirmed empirically during implementation (not assumed from the design doc): file/class scope names in the symbol table are always lowercase — the lexer lowercases filenames before parsing — even though `IFile.name` in the editor preserves whatever case the user gave the file, so every scope-name comparison in `symbolCatalogue.ts` lowercases both sides.

### Remaining scope
None — all deliverables above are done. Milestone 2 shipped as `v0.4.0`.

### Post-ship fixes
Real-world validation after `v0.4.0` shipped surfaced two bugs in the dynamic symbol resolution feature — both invisible in unit tests because every test fixture used pre-normalized/pre-stripped names rather than the actual shapes flowing through the running app:

- **`v0.4.2`** — Two compounding bugs in `completions.ts` broke autocomplete filtering the moment any prefix was typed (i.e. normal usage): `parseCompletionModule`'s regex required a bare trailing dot, so typing a filter character after it (`ship.setSc`) made the owner unresolvable and completion silently fell back to unrelated suggestions; separately, the suggestion `range` was a zero-width point at the cursor rather than spanning the typed prefix, breaking Monaco's own built-in filtering/ranking for whatever *was* returned. Hover was unaffected — it resolves via Monaco's own `getWordAtPosition` (an already-complete token), not this regex-based partial parsing.
- **Earlier in the `v0.4.x` line** — `Editor`'s `SymbolContext.getActiveFilename()` passed the raw `IFile.name` (e.g. `Main.bas`, with extension and casing preserved) into symbol-table scope-name lookups, but the symbol table always scopes symbols under the extension-stripped, lowercased filename (`main`). This broke dot-completion on any object instance (`ship.` for a `sprite`) and bare-word completion of anything scoped to a file's own module rather than global.

Both were found via live reproduction against the running app (not just unit tests) after a user report that autocomplete "didn't work at all." Worth remembering when adding intellisense-adjacent tests going forward: fixtures need to carry the real shapes (`Main.bas`, not `main`; a typed-but-incomplete prefix, not just an empty one) or they'll validate the wrong thing.

## Perpetual parking lot

Items that don't fit cleanly into the milestone sequence but should be revisited periodically:

- **`not` can't appear after `and`/`or`** — `if X and not Y() then` fails to compile ("Expected String, Number, Variable but found not"); only `if not Y() and X then` (leading `not`) works. Root cause: `BoolExpressionRule` calls the `Not` rule exactly once, up front, before its own `and`/`or` loop; `AndRule`/`OrRule` then parse their right-hand side as a plain `BoolTerm`, which never routes back through `Not`. So a leading `not` is fine, but `not` anywhere after the first `and`/`or` isn't reachable from the grammar at all. Discovered 2026-08-30 writing Raycaster's zombie-groan trigger (`if not zombieGroan.isPlaying() and zombieGroanCooldown <= 0 then` compiles; the same condition with the two operands swapped doesn't) — worked around there by reordering rather than fixing the grammar. Likely affects any boolean expression mixing `and`/`or` with a `not` on anything but the first operand; no test currently guards this shape (`tests/lib/Basic4WebGL/unit/transpiler/control.test.ts` has no case combining them). Fix would be in `AndRule`/`OrRule`, having their right-hand side parse via `Not` instead of `BoolTerm` directly — small, localized change, but untried; revisit if it bites again or when doing a general boolean-expression grammar pass.
- **Multiplayer / real-time co-editing** — requires account infrastructure (M4) as a prerequisite. Significant complexity beyond that.
- **Team / organisation tier** — shared projects, multiple seats. Natural extension after paid tier (M8).
- **Game embedding** — embed a published game in an external site via `<iframe>`. Possible extension of M5 sharing infrastructure.
- **Configurable fixed-timestep simulation rate** — `frameloop.js`'s `FIXED_STEP_MS` (`1000 / 60`, i.e. 60Hz) is hardcoded, not per-scene configurable. Deliberate for now, not an oversight: raised 2026-08-25 while explaining the fixed-timestep + interpolation rework (shipped 2026-08-24, see v0.6.16 in `src/docs/release-notes.md`) to the user, who correctly wanted to confirm a hardcoded 60Hz wasn't reintroducing the display-rate coupling that rework had just fixed. It isn't: simulation (kinematics, pathfinding, tween) steps at a fixed 60Hz regardless of display refresh, while rendering still happens every real frame (confirmed live on a >60Hz monitor) via interpolation between the last two simulation samples — `_sbFrameLoop._update` calls `_renderPrepare()` unconditionally every tick even when zero fixed steps ran that frame. Cross-checked against Godot's `_physics_process` (fixed-rate, default 60Hz, a project setting) plus its 4.x Physics Interpolation feature, which does the same simulation/render split for the same stated reason (smooth motion on high-refresh displays without raising the physics rate) — this codebase converged on the same architecture independently. 60Hz matches every existing demo's tuned speed/timing constants (`Player.bas`'s `speed = 100`, `attackCooldown = 0.4`, pathfinding's 200ms recompute interval, etc.), so leaving it fixed keeps that tuning meaning what it already means. If a future demo genuinely needs tighter simulation granularity (a physics-precision-sensitive genre, unlike anything shipped so far), making `FIXED_STEP_MS` per-scene configurable — mirroring Godot's project-setting approach — would be a contained addition, not a redesign. No planned timeline; revisit only if a real need surfaces.
- **Block-level lexical scoping** (`if`/`endif`, `for`/`next`, `while`/`endwhile`, `do`/`until`) — currently intentional, not a bug: only `Function`, `Constructor`, and the per-file `Class`/module scope push onto `Symbols`' scope stack (`RootRule`, `FunctionRule`, `ConstructorRule`). A `dim` inside an `if` is visible for the rest of the enclosing function; blocks don't shadow or scope variables. No decision has been made yet on whether/how to tighten this — it has real design questions of its own (shadowing rules, error messages for use-outside-block). Revisit deliberately, not as a side effect of other work. Consequence noted during the M2 dynamic-symbol-resolution design (2026-08-01): that feature's editor-side scope scanner intentionally matches current compiler semantics (block dims visible to the whole enclosing function) rather than anticipating this — if block scoping ever lands, the compiler will need per-block loc ranges for its own error-checking anyway, and the editor scanner should switch to reading those ranges rather than reimplementing block-counting logic itself.
- ~~Inline array-literal syntax~~ **[DONE — shipped 2026-08-07]** (`{1, 2, 3}` / `{"walls", "obstacles"}`) — softBASIC currently has no array-literal syntax; arrays are built via `dim arr(N)` + repeated `array.push(arr, item)` calls. Raised 2026-08-07 as an aside during pathfinding-module design — wanting to write `pathfinding.setup(tileMapSet, ["walls", "obstacles"])` inline as a call argument instead of declaring+pushing across multiple lines; treat that module name as incidental, this is a standalone language feature. Feasibility explored 2026-08-07: **medium-sized**, not large. The expression grammar has exactly one clean insertion point (`FactorRule.ts`, where every terminal expression form bottoms out), so a literal wired in there is automatically legal everywhere an expression is legal — including as a bare function-call argument, with no temp-variable desugaring needed. Needs a new `ArrayLiteralNode`, a parser branch/rule, and a transpiler rule emitting a plain JS array literal via the existing `concatChildren` codegen helper. No changes needed to `symbolTypes.ts`: recommend keeping literal-initialized arrays as loosely-typed `Variable`/Variant (consistent with the rest of the untyped array system), reusing the existing runtime-checked `_sbCheckedArrayGet` indexing path rather than promoting to a compile-time `ArraySymbol`. **Delimiter decision: `{` / `}`, not `[` / `]`.** softBASIC already spends `[]` on dictionaries (`dim d[]`, `d["key"]`) while arrays use `()` for both declaration and indexing (`dim arr(N)`, `arr(i)`); reusing `[]` for array literals too would make the same bracket carry two conceptually unrelated meanings (dict vs. ordered collection), disambiguated only by position — workable grammatically (no actual parser ambiguity, since dict-bracket contexts and literal-expression contexts never overlap) but a needless readability cost for the beginner audience these docs target. `{}` is entirely unused in the language today, keeps "one bracket, one meaning," and leaves `{"key": "value"}` sitting there as the obvious future dict-literal syntax. An `array.of(1,2,3)`-style variadic function was also considered and rejected: the language has no variadic-argument support, so that would mean hardcoding one function's arity into the compiler rather than reusing general grammar. Shipped 2026-08-07 exactly as designed: `OpenBrace`/`CloseBrace` tokens, `ArrayLiteralNode`, the `FactorRule` parser branch, and the transpiler rule all landed with tests (`tests/lib/Basic4WebGL/unit/transpiler/arrayLiterals.test.ts`) and docs (`src/docs/language-guide/arrays.md`). Plan: `docs/superpowers/plans/2026-08-07-array-literal-syntax.md`.
