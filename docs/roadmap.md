# softBASIC — Internal Product Roadmap

> Internal document. Not for publication. Last updated: 2026-08-04.

---

## Versioning model

**Trunk-based development.** All work lands on `main`. Patch bumps (`0.x.Y`) are continuous — any fix, doc update, or small feature that ships independently. Minor bumps (`0.X.0`) mark milestone completions, each representing a discrete capability step. Currently at `v0.4.3`, but this understates where things actually are: Milestone 1 shipped as `v0.3.0`, Milestone 2 (professional editor) shipped as `v0.4.0` — but **Milestone 3 (save/load) was never given its own version bump or release-notes entry**, despite closing out a whole milestone (which the versioning model itself says warrants a *minor* bump, not a patch). `v0.4.1`/`v0.4.2` covered unrelated editor bug fixes that happened to land around the same time; `v0.4.3` covers a compiler-limitation fix discovered *while building* Milestone 3 (see "Known deferred issues" #6 below) — but the feature itself was folded into the version-number background noise rather than announced. **This needs a proper `v0.5.0` cut before calling Milestone 3 actually released**, not just implemented.

**Public beta vs. v1.0:** these are two distinct bars, not the same milestone. Public beta (Milestone 3) means someone can design, build, and ship a complete game anonymously — gated on game state save/load, not accounts. (Production error tracking was also on this list until scoping the milestone turned up that it's already shipped — see Milestone 3.) v1.0 (Milestone 6) additionally requires accounts, sharing, the gallery, and the package ecosystem (Milestones 4–6). Reframed 2026-08-02 after concluding accounts weren't actually the missing link for "can someone build a full game" — persistent state was.

Milestones 1–6 are fully defined. Milestones 7–14 are intentionally loose — trajectory markers only. Each will be fully scoped and planned before implementation begins, so detail accumulates just-in-time rather than speculating years ahead.

## Current state (v0.4.3)

Shipped and working:
- Full softBASIC compiler (lexer → parser → transpiler → PIXI.js runtime)
- Sprite, animatedsprite, tilemap, text, drawing, audio, collision, input modules
- Scene management (`Scene` base class + `SceneManager`), camera (`camera` module), and world/HUD layers (`world` + `hud`, replacing the deprecated `stage` module) — closes out Milestone 1
- Professional Monaco-based editor — autocomplete, hover documentation, parameter hints, live error underlining, and dynamic symbol resolution (user-defined functions/classes/variables, not just the built-in library) — closes out Milestone 2, see below
- Typed collections, class inheritance, `new` keyword, dependency-ordered multi-file builds
- Folder system, asset panel, import/export, package registry
- Landing page with live game preview
- Demos page, launched with a Wolfenstein-style raycaster tech demo
- Production error tracking (Sentry) — React app crashes and sandboxed game-iframe runtime errors both captured, the latter with full project source attached for reproduction; shipped 2026-06-17, DSN confirmed live in the production deployment
- `oninit` lifecycle hook — the only hook that runs *before* asset preloading, so a project can configure the runtime while there are still no textures (shipped 2026-08-04, see `docs/language/library-roadmap.md` P11). Closed a genuine language gap: every other hook fired post-preload, so there was no init phase at all. Required two-phase module initialisation in the transpiler — a root's inert declarations are emitted inline while its own top-level statements are deferred to `_sb._deferModuleBody` and replayed after preload — which is what let the transpiled block move ahead of asset loading in `bootstrapper.html`
- `world.setPixelPerfect(v)` and `camera.setZoom(z)`/`camera.zoom()` — crisp pixel-art scaling plus a camera zoom that magnifies the whole world uniformly (tilemap, sprites, everything) without touching any object's own position/collision math (shipped 2026-08-04, see `docs/language/library-roadmap.md` P12). `setPixelPerfect` is the direct payoff of `oninit` existing: called before any texture loads, it needs no retroactive fix-up

Building this also surfaced and fixed a real, pre-existing compiler bug — `ObjectType` was missing `'Variant'` from its `acceptsTypes` (unlike every other concrete type), so assigning a function's return value to an object-typed variable (`dim x as ClassName`) could never type-check; see the fix commit and `tests/lib/Basic4WebGL/unit/transpiler/objectVariantAssignment.test.ts`. This closes the prerequisite engine gap for **Milestone 12 (Tilemap editor)** below — the editor itself (painting UI, load/save, tile palette) remains unscheduled.

12. ~~Calling a method on a **function-scoped** object local and using its **return value in an expression** emitted a name that is `undefined` at runtime~~ **[RESOLVED, 2026-08-04]** — `dim s as sprite(...)` inside a function compiled correctly for its constructor assignment and for void method calls used as bare statements, but `print string.str(s.width())` emitted `main.onenter.s.width()` instead of `onenter_s.width()`, throwing `Cannot read properties of undefined`. Root cause was **not** `formatSymbol` (where the wrong string merely became visible): two parser rules handle `obj.method(...)` depending on grammatical context, and they derived the call target from different sources of truth. The statement path (`ObjectPropertyRule`) builds it from the *instance* symbol via `formatSymbol(ownerSymbol)`; the expression path (`VariableFactorRule`) computed exactly the same value and then **discarded it**, delegating to `FunctionFactorRule` so that `FunctionTermRule` re-derived the callee from the *method* symbol's `fullScope` — the lexical scope chain recorded by `Symbols.clone()` at declaration time (`main.onenter.s`). That is a declaration path, not a JS access path, and the two only coincide for **module-scoped** instances (`main.s` === `main.s`), which is why nothing caught it: every shipped tutorial reaches instance members through `self.x` (a separate rule) or declares them at module level. Surfaced while building the coins-platformer demo, which needed `dim t as tilemap(...)` in a scene's `onenter()` and then read `t.tileAt(x, y)`. Fixed by threading the already-resolved receiver from the call site into `FunctionTermNode`, so both contexts now resolve it from the instance symbol and cannot disagree — deliberately keeping `FunctionTermNode` (and therefore `BaseParameterValidatorNode` arity/type checking) rather than switching to the unvalidated `PropertyMethodTermNode` that `SelfFactorRule` uses. Investigation also turned up two shapes the original report assumed were safe: **typed function parameters** (`s as sprite`), which `VariableListRule` registers as Object symbols through the same clone path, and **locals inside class methods**. Gated by `tests/lib/Basic4WebGL/unit/transpiler/objectInstanceScoping.test.ts` (18 tests; 9 failed / 9 passed before the fix, splitting exactly along broken vs. already-correct paths) and `cypress/e2e/objectInstanceScoping.cy.ts` (asserts printed *values*, not just absence of `ERR`, so a program that runs but computes the wrong thing still fails — confirmed non-vacuous by reverting the fix and watching all 4 fail). Design: `docs/superpowers/specs/2026-08-04-object-instance-receiver-resolution-design.md`. Not recorded in `docs/language/library-roadmap.md` — that file's "Fixed Bugs" section tracks runtime engine/library defects, and this changes no softBASIC API surface.
13. ~~A class-scope **array field** indexed through `self` and **read in expression position** transpiled to a JavaScript function call instead of an array index~~ **[RESOLVED, 2026-08-04]** — `v = self.coins(i)` emitted `this.coins(readit_i)` rather than `this.coins[readit_i]`, throwing `this.coins is not a function` at runtime with zero compile diagnostics. Root cause: softBASIC spells array indexing and method calls identically (`name(args)`), so `self.member(...)` is genuinely ambiguous and can only be settled by asking the symbol table what kind of member it is. Two rules handle that form depending on grammatical context, and only one could settle it: the **statement** path (`SelfRule`) disambiguates *syntactically* on a trailing `=` — a method call can never sit on the left of an assignment — so indexed **writes** were always correct and `SelfArrayAssignNode`/`SelfArrayAssignRule` already existed to emit them. The **expression** path (`SelfFactorRule`) has no such lookahead token, must consult the symbol table instead, and never did: it unconditionally returned a `PropertyMethodTermNode` for every `self.x(...)`, despite already performing a class-scope symbol lookup a few lines lower to recover the `dataType` of a non-indexed `self.property` read. The information needed was already being fetched by that rule for another purpose; the ambiguous path just never asked. Survived this long because every shipped tutorial touching a class array either passes it whole to an `array.*` function (bare, unambiguous) or writes by index (disambiguated by `=`) — reading one back by index inside a method is what the coins-platformer demo first needed. Fixed by resolving the member's kind against the enclosing class scope (walking the inheritance chain) via a new `resolveSelfMember` helper and emitting a new `SelfArrayLookupNode` — the read-side mirror of the existing write pair — only when the member is provably an `Array`-kind class member and provably **not** a method. **A method of that name always wins**, which is what makes the change provably non-breaking: no `self.x(...)` that compiles today can change meaning. The pre-existing `dataType` walk in the same rule was folded onto the same helper (semantics preserved exactly via an `accept` predicate) so the two class-scope lookups cannot drift apart. Investigation corrected two assumptions in the original report: indexed **writes** were never broken, and class-scope **dictionary** fields are affected but *differently* — a loud compile error rather than a silent miscompile (see #14). Fixed shapes beyond the reported one: reads in arithmetic, comparisons/`if`, `while` conditions, `print` and module-function arguments, `return`, nested as their own index, multi-dimensional fields (`this.grid[1][2]`), reads inside **constructors**, and **inherited** array fields. Gated by `tests/lib/Basic4WebGL/unit/transpiler/selfArrayFieldAccess.test.ts` (29 tests; 16 failed / 13 passed with the fix disabled, splitting exactly along broken vs. already-correct paths) and `cypress/e2e/selfArrayFieldAccess.cy.ts` (3 specs asserting printed *values*, each writing by index and reading back by index so a regression in either direction changes the output — confirmed non-vacuous by disabling the fix and watching all 3 fail). Design: `docs/superpowers/specs/2026-08-04-self-array-field-indexing-design.md`.
14. **Class-scope collection fields are only reachable through `self` for arrays, and only by plain index** — three related shapes are unimplemented in `SelfFactorRule`/`SelfRule`. All three fail as **loud compile errors**, not silent miscompiles, which is why they were left out of #13's fix rather than folded in: (a) **dictionary fields via `self`** — neither rule has an `OpenBracket` branch, so `self.scores["a"]` fails with `Expected NewLine,EndOfFile,SoftNewLine got OpenBracket` when read and `Expected Equals got OpenBracket` when written; (b) **array/dict fields accessed from outside the class** (`someInstance.items(0)`) — read fails with `Function items ... has not been declared yet`, write with `Expected NewLine,EndOfFile,SoftNewLine got Equals`; (c) **member access on an array element via `self`** (`self.bullets(0).getX()`) — fails with `Expected NewLine,EndOfFile,SoftNewLine got Dot`; `TypedElementAccessNode` already supports exactly this shape for non-`self` arrays (`VariableFactorRule`), so the machinery exists and is simply not wired into the `self` path. Found while root-causing #13; each is a missing feature rather than a defect, and none can produce wrong output at runtime. Note that (a) contradicts the intuition that bracket syntax is "already unambiguous and therefore safe" — it is unambiguous, but no rule ever parses it after `self.`.
15. **A class can declare an array field and a method with the same name with no diagnostic at either declaration site, and it crashes at runtime** — `Symbols.add()`'s duplicate-declaration check is scoped per symbol *kind*, not per name, so `dim items(3)` and `function items()` coexist silently in the same class. `self.items(0)` resolves to the method (per #13's "a method always wins on ambiguity" rule) and emits `this.items(0)` — but the array field's deferred initializer (`_sb._deferModuleBody(...)`) runs *after* class setup and overwrites `prototype.items` with the array, so the method is gone by the time anything calls it: `this.items is not a function` at runtime regardless of which node the compiler chose. Found during #13's code review while stress-testing "method always wins" — confirmed this crashes identically on the commit *before* #13 too, so it is not a regression from that fix, just a pre-existing gap it surfaced. Not yet scheduled: would need either a cross-kind duplicate-declaration check in `Symbols.add()` (reject at compile time) or a naming convention rule; no design work done yet.
16. ~~**Every object instance's own `onupdate(delta)` silently stopped being dispatched by the frame loop** after the first `world.remove()`/`hud.remove()`/`world.clear()`/`hud.clear()`/scene switch~~ **[RESOLVED, 2026-08-04]** — the first **runtime engine** bug of this session rather than a compiler one. Instances added via `world.add()`/`hud.add()` kept correct `onupdate` methods and ran correctly when invoked directly, but the real `app.ticker` loop never called them again; entirely silent, no error of any kind. The report's second half, found during verification and *not* in the original triage, is the mirror symptom: removed objects never **stopped** updating either — `world.remove(enemy)` detached the display handle so the enemy vanished from screen while its `onupdate` ran forever, an invisible zombie still mutating game state. Root cause: `softBasicEngine.js` builds the global `_sb` by spreading all 14 engine modules once at script-eval time, which copies the *reference* held in `_sbLifecycle._sbInstances` into a **second independent property slot** on `_sb`. Mutating the shared array through either slot is safe; **reassigning** either detaches them. `stage.js` reassigned in five places (four `.filter(...)` calls plus `clear()`'s `= []`), each writing the **module's** slot by hardcoded name — while every reader goes through `_sb`: instance dispatch is `_sbLifecycle._update.call(this)` with `this` bound to `_sb`, and `bootstrapper.html`'s key listeners read `_sb._sbInstances` directly (so instance `onkeydown`/`onkeyup` were broken by the same divergence). After the first mutation, `_sb`'s slot held a permanently orphaned array; later `world.add()` calls pushed onto the new one the loop never read again. Those five lines were the **only** writes to a hardcoded module property anywhere in the engine — every other module (`camera`, `scene`, `input`, and `lifecycle`'s own `_deferredModuleBodies`) reads and writes its state through `this`, which is safe precisely because `this` is always `_sb`; `clear()` already calling `this._cameraReset()` (a `camera.js` method) proved that. Fixed by making `stage.js` use `this._sbInstances` like every other module **and** mutating in place only (new `_retainInstances(predicate)` compaction helper on `lifecycle.js`, `length = 0` for `clear()`), so there is one owning slot and the reference can never go stale. That in turn required a per-frame `.slice()` snapshot for instance dispatch: in-place splicing makes `forEach` skip a sibling when an object removes something during its own `onupdate` (`world.remove(self)` when an enemy dies — the commonest pattern in a game), a hazard the old reassign accidentally masked; verified by removing the snapshot and watching two tests fail. **Audit for sibling instances of the hazard found none** — `_sbClasses` confirmed safe (assigned directly onto `_sb` by `terminationRules.ts`, never by a module), and all other module state is `this`-written. Gated by `tests/components/Runner/stage.test.ts` (19 tests that evaluate the real 14-module concatenation *plus* the real spread, so the actual production seam is exercised; 15 failed before the fix, 4 passed incidentally) and `cypress/e2e/instanceUpdateRegistry.cy.ts` (4 specs covering all four triggers, each asserting both a line that must appear and one that must not so the zombie half is caught, each driving a module-level `onupdate` as a control proving frames really ran — confirmed non-vacuous by reverting the engine fix and watching all 4 fail). Survived this long because no Vitest test ever loaded the engine modules *together* (so the spread that creates the second slot existed in no test), Cypress asserted only "no `ERR`" and this bug emits none, and every shipped scene tutorial drives motion from the **scene's** `onupdate` (dispatched via `_activeScene`, unaffected) rather than per-object `onupdate`. Design: `docs/superpowers/specs/2026-08-04-instance-update-registry-aliasing-design.md`.
17. **No built-in solid-tile/platformer collision helper — `tilemap` only exposes single-point `tileAt(x, y)` sampling, so every author must hand-roll AABB collision themselves, and it's easy to silently get wrong.** Discovered 2026-08-04 while playtesting the coins-platformer demo: `Player.bas`'s ground collision only ever sampled one point just below the feet to snap vertically, and applied horizontal movement with **no collision check at all** — so the player could walk into the side of a solid multi-tile-thick ground block after falling past a gap, and the vertical snap would then plant them on whichever interior tile row their feet happened to land inside, visually sinking them into the floor. Not an engine defect — `tileAt(x, y)` is a sufficient primitive, this specific instance was fixed directly in the demo's own collision code (sampling the leading edge before applying horizontal movement, mirroring the existing vertical check) — but given the product's target audience is beginners with no prior coding experience, requiring every author to correctly hand-roll multi-point AABB tile collision (and silently produce this exact bug if they miss one direction, as happened here) is a real usability gap. A future higher-level helper (e.g. a `tilemap`/`collision` function that resolves a moving AABB against solid tiles on all four sides in one call) would remove this whole class of mistake. No design work done yet.
18. ~~**Every softBASIC game ran ~16.67x slower than its own documented contract** — the `delta` handed to every `onupdate(delta)` was PIXI's frame-count-normalised value (~1.0 per frame), not milliseconds~~ **[RESOLVED, 2026-08-04]** — the second **runtime engine** bug of this session, and the most cross-cutting: every moving object in every game, tutorial and demo depended on it. `bootstrapper.html` wired the frame loop as `app.ticker.add((ticker) => _sb._update(ticker.deltaTime))`. PIXI's `Ticker` exposes two different numbers — `deltaTime` is normalised so that 1.0 means "one 60fps frame", while `deltaMS` is the same quantity in milliseconds — and the loop took the wrong one. That value flowed unmodified through `_sb._update(delta)` into every module-level and every instance `onupdate(delta)`. But the contract is milliseconds in three independent places: `src/docs/language-guide/lifecycle.md` ("the elapsed time in milliseconds since the last frame"), `src/docs/api-reference/scene.md` ("Time since last frame in milliseconds"), and every tutorial doing frame-rate-independent movement, which writes `speed * delta / 1000`. So `dt = delta / 1000` computed ~0.001 instead of ~0.01667. Tutorial 7 shows the discrepancy at its most concrete: it accumulates `timer = timer + delta` and tells the reader the score "ticks up by one every second" at `timer >= 1000` — in reality it ticked once every ~16.7 seconds, and inside the e2e suite's own window that branch **never fired at all**. Confirmed by live instrumentation rather than inspection: wrapping the real `_sb._update` over 859 real frames gave a wall clock of 14318.3 ms against a delta sum of 858.99 (ratio **16.67**), and a fresh `PIXI.Ticker` reported `deltaTime` 1.002 alongside `deltaMS` 16.7 on the same frame. Across every sampled frame `deltaMS / deltaTime` was **exactly** `1000/60` with zero variance — which is what makes `deltaMS` provably the correct replacement rather than merely a closer one: it is `deltaTime` scaled by a constant, carrying the identical `ticker.speed` scaling and `minFPS` clamp, so the swap is a pure unit conversion with no behavioural side effect. (`elapsedMS` was rejected for that same reason: it is the raw unclamped measurement and would drop both the speed scaling and the large-gap clamp a backgrounded tab relies on.) **A second site had to change with it**, found by sweeping the engine for delta consumers rather than assuming the one-line fix was complete: `camera.js`'s `_shakeElapsed += (delta || 0) / 60` was written *against* the wrong units — `camera.shake(intensity, duration)` documents `duration` in seconds, and `/ 60` only yields seconds while `delta` is ~1.0 per frame. Left alone, fixing the units would have made every camera shake finish ~16.67x too early (a 0.5s shake completing in 2 frames), and nothing in the suite covered shake duration, so it would have shipped silently. Two near-misses were checked and are genuinely unaffected: `animatedSprite.js`'s `animationSpeed = def.fps / 60` looks like the same mistake but PIXI's `AnimatedSprite` self-drives from `PIXI.Ticker.shared`, a *different ticker object* from `app.ticker` (verified in-browser that they are not identical), and `camera.follow`'s `speed` is documented as a per-frame lerp factor that never reads `delta`. Gated by `cypress/e2e/deltaUnits.cy.ts` (4 specs — module and instance dispatch paths separately, the documented once-per-second tutorial pattern, and the strongest form: accumulated delta compared against `performance.now()` measured over the same window, which pins the *units* and cannot be satisfied by any fixed constant), plus `tests/components/Runner/camera.test.ts` (3 tests on shake duration and fade-out) and 3 static guards in `tests/components/Runner/bootstrapper.test.ts` asserting the wiring reads `deltaMS`. Non-vacuity: every Cypress spec prints a frame-count checkpoint driven by a counter independent of delta's *value*, so a game that never booted fails there rather than passing silently, and every delta assertion is two-sided so an accidental over-scaling is rejected too — confirmed by reverting the fix and watching all 4 fail with messages naming the real bug while their controls still passed. Survived this long because `tutorials.cy.ts` and `demos.cy.ts` contain exactly one assertion each (`ERR` must not exist) and this bug emits no error, Vitest cannot instantiate a `PIXI.Ticker` so no unit test ever saw a real frame delta, and the symptom is uniquely un-alarming: a sprite that moves slowly looks like a sprite with a low `speed` constant, and an author's natural fix — raise `speed` until it looks right — silently bakes the 16.67x error in and destroys the evidence. Introduced by the fix for "Bug 1 — `onupdate()` never fires" (`docs/language/library-roadmap.md`), which correctly connected `_update` to the ticker and picked the wrong one of its two delta properties; because `onupdate` went from never firing to firing, the change read as an unambiguous success and the units were never questioned. Design: `docs/superpowers/specs/2026-08-04-delta-units-fix-design.md`.
19. ~~**The combined `dim x as ClassName = <expr>` form only accepted a literal `new ClassName(args)` on the right-hand side — any other expression (e.g. a method call) failed to parse**~~ **[RESOLVED, 2026-08-05]** — `DimRule.ts`'s `Equals` branch unconditionally called `matchAndMove(tokens.New, ...)` immediately after `=`, so `dim fg as tilemaplayer = tm.layer("foreground")` failed with `Expected New got Variable`, even though the equivalent two-statement form (`dim fg as tilemaplayer` then a separate `fg = tm.layer("foreground")`) already worked (see issue #10's `TileMapSet` fix, which made `ObjectType` accept `Variant`-typed expressions). ## ~~Milestone 2 — Professional editor~~ **[DONE — shipped as v0.4.0, 2026-08-01]**

**Goal:** Make the editor credible for sustained use. Full intellisense backed by the existing `.bas` definition files.

### Deliverables
- ~~**Editor replaced with Monaco**~~ **[DONE]** — `@monaco-editor/react` integrated in `src/components/Editor/index.tsx`, replacing the old textarea.
- ~~**Autocomplete**~~ **[DONE]** — live via `src/monacoHelpers/completions.ts`, registered in `Editor/index.tsx`. Resolves the static library catalogue first (module functions, class methods, constructors); falls back to user-defined functions, classes, and in-scope variables via a dynamic symbol snapshot when the static catalogue doesn't know the name.
- ~~**Hover documentation**~~ **[DONE]** — live via `src/monacoHelpers/hover.ts`, same static-first/dynamic-fallback resolution as autocomplete.
- ~~**Parameter hints**~~ **[DONE]** — live via `src/monacoHelpers/signatures.ts`, same static-first/dynamic-fallback resolution, including correctly showing constructor parameters (see "Dynamic symbol resolution" below).
- ~~**Error underlining**~~ **[DONE]** — `useLiveAnalysis` (renamed from `useLiveDiagnostics`) silently debounces (~450ms) a `Basic4WebGL.transpile()` call and `Editor` maps the resulting diagnostic to a Monaco marker via `monacoHelpers/diagnostics.ts#toMarkers`, squiggling only the active file live as the developer types. Cross-file errors are surfaced by making error entries in the bottom console clickable — `BottomPanel`'s `onJumpToLoc` switches the selected file and moves the cursor. Live/debounced diagnostics and jump-clicks never write a console log entry or auto-switch tabs on their own — only the explicit Build/Run path and explicit clicks touch console/tab state.
- ~~**Dynamic symbol resolution**~~ **[DONE]** (2026-08-01) — `Symbols.getSnapshot()` exposes a serializable flat symbol table; `Basic4WebGL.transpile()` returns it on a clean compile. `useLiveAnalysis` caches this snapshot with **last-known-good** semantics — it only advances on a zero-diagnostic compile, so intellisense reflects the file as of its last successful compile rather than the literal (possibly broken) current buffer, same staleness tolerance already accepted for error underlining. A new `monacoHelpers/scopeScanner.ts` textually tracks live `function`/`endfunction` and `constructor`/`endconstructor` nesting at the cursor, independent of the compiler, so it stays correct even while the buffer doesn't compile — deliberately does not track `if`/`for`/`while`/`do`, matching the compiler's existing function/constructor-only scoping (see "Block-level lexical scoping" in the parking lot below). `monacoHelpers/symbolCatalogue.ts` is the dynamic mirror of the static `catalogue.ts`; the static catalogue always wins on a name conflict. Confirmed empirically during implementation (not assumed from the design doc): file/class scope names in the symbol table are always lowercase — the lexer lowercases filenames before parsing — even though `IFile.name` in the editor preserves whatever case the user gave the file, so every scope-name comparison in `symbolCatalogue.ts` lowercases both sides.

### Remaining scope
None — all deliverables above are done. Milestone 2 shipped as `v0.4.0`.

### Post-ship fixes
Real-world validation after `v0.4.0` shipped surfaced two bugs in the dynamic symbol resolution feature — both invisible in unit tests because every test fixture used pre-normalized/pre-stripped names rather than the actual shapes flowing through the running app:

- **`v0.4.2`** — Two compounding bugs in `completions.ts` broke autocomplete filtering the moment any prefix was typed (i.e. normal usage): `parseCompletionModule`'s regex required a bare trailing dot, so typing a filter character after it (`ship.setSc`) made the owner unresolvable and completion silently fell back to unrelated suggestions; separately, the suggestion `range` was a zero-width point at the cursor rather than spanning the typed prefix, breaking Monaco's own built-in filtering/ranking for whatever *was* returned. Hover was unaffected — it resolves via Monaco's own `getWordAtPosition` (an already-complete token), not this regex-based partial parsing.
- **Earlier in the `v0.4.x` line** — `Editor`'s `SymbolContext.getActiveFilename()` passed the raw `IFile.name` (e.g. `Main.bas`, with extension and casing preserved) into symbol-table scope-name lookups, but the symbol table always scopes symbols under the extension-stripped, lowercased filename (`main`). This broke dot-completion on any object instance (`ship.` for a `sprite`) and bare-word completion of anything scoped to a file's own module rather than global.

Both were found via live reproduction against the running app (not just unit tests) after a user report that autocomplete "didn't work at all." Worth remembering when adding intellisense-adjacent tests going forward: fixtures need to carry the real shapes (`Main.bas`, not `main`; a typed-but-incomplete prefix, not just an empty one) or they'll validate the wrong thing.

## Perpetual parking lot

Items that don't fit cleanly into the milestone sequence but should be revisited periodically:

- **Multiplayer / real-time co-editing** — requires account infrastructure (M4) as a prerequisite. Significant complexity beyond that.
- **Spritesheet editor** — may be pulled into M11 (sprite editor) depending on scope decisions there.
- **Team / organisation tier** — shared projects, multiple seats. Natural extension after paid tier (M8).
- **Game embedding** — embed a published game in an external site via `<iframe>`. Possible extension of M5 sharing infrastructure.
- **Block-level lexical scoping** (`if`/`endif`, `for`/`next`, `while`/`endwhile`, `do`/`until`) — currently intentional, not a bug: only `Function`, `Constructor`, and the per-file `Class`/module scope push onto `Symbols`' scope stack (`RootRule`, `FunctionRule`, `ConstructorRule`). A `dim` inside an `if` is visible for the rest of the enclosing function; blocks don't shadow or scope variables. No decision has been made yet on whether/how to tighten this — it has real design questions of its own (shadowing rules, error messages for use-outside-block). Revisit deliberately, not as a side effect of other work. Consequence noted during the M2 dynamic-symbol-resolution design (2026-08-01): that feature's editor-side scope scanner intentionally matches current compiler semantics (block dims visible to the whole enclosing function) rather than anticipating this — if block scoping ever lands, the compiler will need per-block loc ranges for its own error-checking anyway, and the editor scanner should switch to reading those ranges rather than reimplementing block-counting logic itself.
