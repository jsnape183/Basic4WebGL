# AI chat agent (in-editor code generation) — POC direction notes

**Status: discussion capture, not an active plan.** This document records decisions reached in an exploratory conversation about how Milestone 7 ("AI-assisted development") might work if it uses a self-hosted-style small model instead of a frontier-model API. **Nothing here is scheduled or implemented.** Milestone 7 itself is gated on Milestone 4 (account infrastructure) landing first — this doc exists so that gating discussion isn't lost in the meantime, and so M7 planning can start from resolved ground instead of re-deriving it.

---

## Context

Milestone 7 (`docs/roadmap.md`) originally assumed a Claude API integration for in-editor AI assistance. A separate conversation explored a narrower, cheaper variant: an **in-app chat agent that writes softBASIC code from a user's natural-language prompt** — not a tool for developing the language itself, and not full multi-file autonomous editing. That narrower framing is small enough that a self-hosted-style small language model becomes viable, which opens up a materially cheaper cost structure than a frontier-model API. This doc captures the resulting decisions.

---

## Model & hosting decision

**Chosen direction:** Qwen2.5-Coder, served through a token-billed PaaS (Fireworks AI), not a self-managed GPU rental and not a frontier-model API.

Why this shape, over the alternatives considered:

- **Raw GPU rental (RunPod, Lambda Labs, etc.)** — rejected for this use case. You pay for the box whether or not anyone is using the feature, which only makes sense once traffic is steady and high. Wrong shape for an unproven, low-traffic feature.
- **Frontier-model API (Claude/GPT-class)** — still the fallback for anything requiring broad reasoning, but for narrowly-scoped "write this snippet" requests it's roughly **30x more expensive per request** than the Qwen2.5-Coder/Fireworks path (see cost analysis below), for a domain (softBASIC) where a frontier model has no real language-familiarity advantage since the language is obscure and not in typical training corpora either way.
- **Token-billed PaaS running an open coding model (Fireworks)** — chosen. Zero fixed cost, scales to zero when unused, and Qwen2.5-Coder is a real fit for this domain: the task is narrow (reproduce a closed, well-documented API surface — the `.bas` def files — rather than requiring broad world knowledge), and quality can be improved further via RAG (feeding relevant `.bas` defs/docs as context) or distillation (fine-tuning on synthetic prompt→code pairs generated by a frontier model against the real API surface).

**Model size — open question, not yet resolved:** Qwen2.5-Coder-14B is confirmed at $0.20/M tokens (input and output) on Fireworks. Qwen2.5-Coder-32B would likely give better softBASIC syntax accuracy but its exact Fireworks price wasn't confirmed during this discussion — needs checking against Fireworks' live pricing page before committing. Deciding between the two requires testing real prompts against both, which is future work, not something to guess at here.

## Cost analysis

**Per-request assumptions** (to be validated against real usage once built):
- ~1,300 input tokens (system prompt + relevant `.bas` API context pulled in via RAG + the user's own prompt)
- ~400 output tokens (a generated code snippet)
- Qwen2.5-Coder-14B @ $0.20/M tokens (input and output same rate)

Cost per request: (1,300 + 400) / 1,000,000 × $0.20 ≈ **$0.00034**.

**Scaling table** (10 requests/user/day, 30-day month):

| Users | Requests/month | Monthly cost |
|---|---|---|
| 10 | 3,000 | ~$1.02 |
| 100 | 30,000 | ~$10.20 |
| 1,000 | 300,000 | ~$102 |
| 10,000 | 3,000,000 | ~$1,020 |

Even at 10x heavier usage per user (100 requests/day each), 10 users costs roughly **$10/month**. There is no idle-infrastructure cost, so low/unproven adoption carries no financial risk.

**Reference comparison** against a frontier-model API (~$3/M input + $15/M output, Claude/GPT-class): the same request costs ~$0.0099 — about **30x more expensive per generation** than the Qwen2.5-Coder/Fireworks path. The tradeoff is quality on anything beyond fairly templated code generation; this needs validating against real prompts before being treated as a settled win, since a 30x token-cost saving is meaningless if it produces meaningfully worse code and increases support burden.

## Required architecture: a backend proxy

**This project currently has no backend at all** (per `CLAUDE.md`: "There is no backend"). That is a hard blocker for this feature specifically, independent of the M4 gating: **the Fireworks API key must never be embedded in client-side code.** If it were, anyone could extract it from the browser bundle/network tab and call Fireworks directly, bypassing the app entirely — at which point no app-level auth, quota, or rate limiting has any effect, since none of it sits in the actual request path.

Required flow, once this is built:

1. **Browser → backend**: authenticated request (the user's session/account from M4), no Fireworks key present client-side.
2. **Backend**: verifies the user is logged in, checks their per-user quota (requests-today / tokens-this-month against a store), and only if under quota, calls Fireworks using a server-held key.
3. **Fireworks → backend → browser**: response passed back through.

This can be a single serverless function (Cloudflare Worker, Vercel/Netlify function) or a small persistent service — which of those wasn't decided in this discussion and is a real open question for the eventual implementation plan.

## Spend & abuse controls

Two independent layers, both needed:

- **Fireworks' account-wide budget cap** — a monthly spend limit set in the Fireworks dashboard; once hit, *all* API requests pause automatically (serverless inference, deployments, fine-tuning) until raised. New accounts default to Tier 1, capped at $50/month max, so there's a manual step between "default" and a large bill. This is the backstop, not the primary control — it protects the account as a whole, not any individual user.
- **App-level per-user rate limit/quota** — must live in the backend proxy described above, since it's the only layer that knows which user is making a request. This is the layer that actually prevents one user (or a bug/retry loop in the frontend) from burning disproportionate budget, and it's what makes "locked to user accounts" meaningful rather than just a login wall in front of an otherwise-open API.

Fireworks' own rate limiting (6,000 RPM account-wide once a payment method is added, 10 RPM without one) is a coarse, account-wide ceiling against abuse/runaway loops — not a substitute for per-user quota enforcement.

## Open questions

Carried forward from Milestone 7's existing list in `docs/roadmap.md`, with what this discussion resolved vs. left open:

- ~~Which model?~~ **Resolved (direction only):** Qwen2.5-Coder via Fireworks for the narrow "generate code from prompt" case; a frontier model (e.g. Claude) likely still needed for anything requiring broader reasoning (multi-file edits, error diagnosis) — Milestone 7's original framing may need to split into "generation" vs. "assistance" sub-features with different model backing, not a single model decision.
- **Still open:** exact model size (14B vs. 32B vs. others) — needs real-prompt testing.
- **Still open:** what context is actually sent per request (how much of the `.bas` defs / docs get included, and how — static RAG corpus vs. dynamically selected per prompt).
- **Still open:** free tier token allowances / paid tier limits (ties into Milestone 8 pricing, which is itself TBD).
- **Still open:** prompt injection mitigation — a user's own game code or prompt text reaching the model as context is a real vector; not discussed in depth in this conversation.
- **Still open:** backend hosting shape — serverless function vs. small persistent service, and where per-user quota state is stored.
- **New:** whether a distilled/fine-tuned model (using a frontier model to generate synthetic softBASIC training pairs against the real `.bas` API surface) is worth the upfront investment over RAG-only, given the domain's small, closed API surface.
